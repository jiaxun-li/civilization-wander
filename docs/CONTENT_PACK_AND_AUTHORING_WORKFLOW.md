# V5 内容包新增指南

状态：正式内容的生产、审稿、置入与复盘指导文件。

本文用于指导每一次新增内容包。`ContentPack` 只是编辑协作和审稿单位，不是运行时对象、源码文件类型或面向用户的概念。是否新建内容文件不是预设答案；每次任务开始时必须先确认数据存放位置，以及新建文件还是复用现有文件。

实际开工时可复制 `docs/CONTENT_PACK_TEMPLATE.md` 作为三阶段记录底稿。

## 产品核心目标

让用户从一个历史故事出发，沿着人物、事件、制度和思想之间真实而有意义的联系，自由走进另一个故事，逐渐发现一个彼此连接的文明世界。

产品不是让用户按顺序读完一部历史教材，也不是在地图上查找地点，而是提供一种由好奇心驱动的“历史漫游”：

```text
读一个故事
→ 遇见一个关键人物、事件或关系
→ 选择自己感兴趣的新视角
→ 进入另一个完整故事
→ 逐渐形成自己的历史认知网络
```

每次只向用户呈现一个聚焦、完整的故事；每个下一步都应来自有叙事意义的主动选择。地图、图片和动画用于帮助理解具体故事并营造阅读氛围，不是产品本身。

## 最高优先级公共写作原则：少点专有名字，多点故事

这是所有正式内容必须优先满足的公共写作原则，其优先级不低于事实准确、选题聚焦和叙事完整：研究过程可以专业，面向读者的文字必须先成为一个可进入、可跟随的故事。

公共正文与内部研究材料是两种不同产物。来源、Claim ledger、Entity、Event、StructuralEdge 和 EditorialReview 中记录了某个名称、关系、争议或限制，不代表它必须进入公共正文。Event、Entity、关系与来源的完整是数据要求，不是正文逐项点名的要求。

- Card 引言通常只用一至两句话打开好奇，不承担背景综述；故事成立所必需的时代、地点和证据背景进入第一个 Scene，并随叙事展开；
- Scene 优先写具体的人、物件、行动、处境和变化，让读者先看见“发生了什么”，再理解它意味着什么；
- 专有名字是否可以进入正文，只取决于它是否推动当前故事，不取决于它是否已有独立 Card、是否属于本次内容包，或相关扩展包是否已经制作。承担主要人物、参与者、关键地点、事件转折、制度变化、历史判断或跨故事连接作用的名称可以保留；
- 一个名字若删去后不影响人物关系、事件推进、历史判断或跨故事连接，应改成日常指称，或移入来源、内部说明和后续专门故事。不得用跨 Card、跨内容包或全局的专名数量上限代替这项判断；
- 默认读者不熟悉历史，但对历史感兴趣，并且可能从任意 Card 进入。即使名称已经在其他 Card 出现，只要当前理解需要，仍须在本 Card 中用最短的日常语言重新建立它在眼前故事中的作用；
- “首次出现必须解释”不是引入更多名称的许可。首次出现且无法省略的名称，应立即说明它是谁或是什么、正在做什么，以及为什么与眼前的故事有关；若一句或一小段需要连续解释多个名称，应调整叙事顺序逐个引入，而不是压缩成名称清单；
- 除非 Card 本身讲述史学史、思想史、考古研究史或某位学者，现代学者姓名、学派、观点阵营和争论过程默认只进入来源或 EditorialReview。公共正文给出证据支持的最窄综合表述，不用学术争论的目录代替故事；
- **大幅减少防御性文字。** 公共正文使用证据支持的最窄正面表述；更完整的限制、反例、争议和替代解释进入内部 EditorialReview，而不是分散到每个 Scene；
- 只有省略某项不确定性会实质改变当前故事含义、把推测写成事实，或强化一种广泛流传且会误导主线的说法时，才在公共正文保留一次简短限定。限定应紧贴相关句子，不得成为段落的主要内容，也不得让多个 Scene 连续以否定句收尾；
- 第二阶段审稿时必须单独检查：正文是否被专有名字压住，保留名称是否各有明确叙事作用，是否有具体行动或变化推动阅读，引言是否挤占了第一个 Scene 应承担的故事，以及删去防御性句子后故事是否反而更清楚。若能删去而不造成过度断言，就必须删除或移入 EditorialReview；
- 第二阶段及此后的对用户审稿材料一律不设置或输出逐 Card 或逐 Scene 的负面结论上限栏目。证据边界在 Claim ledger 的正面表述、证据强度和去向中维护，必要的限制、反例、争议与替代解释统一进入内部 EditorialReview；不得把它们重新包装成逐段审校提示。

## 1. 内容包定义

每个内容包通常以一个规划入口 `Entity` 为中心，但内容包不等同于 `Entity` 数据对象，规划入口也不等同于每张 Card 的主 Entity。

- 内容包规划入口是本次内容工作的稳定知识入口，只服务选题、协作和审稿，不写入运行时 `ContentPack` 对象；
- 内容包是一套围绕该入口组织的待审材料；
- 一个内容包可以包含一个或多个 Card，以及所需的 Scene、Event、关系、导航、媒体和来源建议；
- 每张 Card 必须根据自己实际讲述的主体选择一个主 Entity，并写入必填的 `primaryEntityId`；
- 内容包只有一张 Card 时，两者可以是同一个 Entity，但不得默认等同；内容包包含多张 Card 时，各 Card 可以拥有不同的主 Entity；
- 一个 Entity 可以关联多个 Card，不设固定数量或上限；
- 比较型或跨区域内容包若无法合理确定统一的规划入口，应先由用户决定范围，不得为了满足模板虚构 Entity；但其中每张进入运行时的 Card 仍必须有自己的主 Entity；
- 内容包的名称和内部组织不进入公共界面。

```text
Entity = 稳定的知识身份
ContentPack = 一次围绕规划入口组织的内容生产与审稿材料
Card = 面向读者的完整故事和主要探索入口，并拥有自己的主 Entity
Scene = Card 内有顺序的叙事与呈现段落
Event = 可被不同故事引用的历史事件
```

## 2. 三阶段工作流

所有正式内容任务固定分为三个阶段：第一、第二阶段分别等待用户批准；第三阶段默认连续完成并提交最终验收，只有下述明确例外才中途暂停：

1. 选题简报；
2. 来源、Claim ledger，以及 Card 和完整待审 Scene 正文；Scene 通常为 `3–11` 个，但不是数量门禁；本阶段内部依次完成证据整理、故事写作和公共文字删减，但仍在同一轮提交、等待一次批准；Scene 数量由该 Card 的重要性与完整叙事需要决定；
3. 为已批准正文选择媒体，直接置入 V5，完成验证与流程复盘，并提议新增的 content 方向。

第一、第二阶段分别完成、分别等待批准。用户没有明确批准第二阶段的来源、Claim ledger 与正文，并要求进入第三阶段或表达同等明确授权前，不得修改项目文件或运行时数据。第三阶段默认不把媒体、置入和验证拆成额外审批点；Agent 应连续完成这些工作后一次性提交最终验收结果。只有媒体缺口、AI／自制示意图需要明确批准，或结构无法忠实表达时，才作为例外暂停相关部分。

每轮输出必须将“内容产物”和“流程改进建议”分开。流程建议只能标记为：

- 通用规则；
- 当前选题特例；
- 实现问题；
- 尚待验证。

流程建议只有经用户明确批准后才能写入本指南。

## 3. 第一阶段：选题简报

开始研究前，先检查实际运行时与现有数据组织，并请用户确认：

- 本次内容写入哪个数据文件；
- 新建独立内容文件，还是复用现有文件；
- 若新建文件，它如何被聚合、按什么顺序加载；
- 主题与内容包规划入口 Entity；若本次包含多张 Card，还要分别列出每张 Card 的暂定主 Entity；
- 每张 Card 主 Entity 的类型必须从当前数据已经使用或用户已经明确批准的 Entity 类型中选择，并且拥有稳定的公共中文标签；未经用户明确允许，不得新增其他 Entity 类型。若现有类型都不合适，或类型尚无公共标签，应在第一阶段报告实现问题并等待决定；
- 当前用户已明确批准可用的新增 Entity 类型为 `IdeaSchool`、`SettlementSite`、`GeographicFeature`、`TextDocument`、`CulturalObject`、`Commodity`、`wonder`、`religionAndMyth`；
- 分别检查内容包规划入口与每张 Card 主 Entity，不得把规划入口直接复制给所有 Card；Card 主 Entity 的稳定知识身份必须真正对应该 Card 主题，不得用范围更广、性质不同或仅仅相关的 Entity 代替故事实际讲述的主体；
- 目标读者和读者最可能产生的好奇；
- 希望回答的核心问题；
- 是否希望连接到某个现有 Card；
- 是否已有可采用的来源或图片。

选题简报至少包含：

- 工作定义：本次所说的主题具体指什么；
- 核心叙事假设：这张 Card 准备讲清哪一个变化；
- 三层时间范围：主叙事时段、必要前史、必要后续；
- 用户好奇入口：为什么读者会想点开；
- 选题边界；第一阶段不设置或输出“明确不写”固定栏目，只有边界问题会实质影响选题成立或造成证据越界时，才将其记入“主要证据缺口或选题风险”；
- 数据文件决策及理由。

Agent 应检查题目是否过大、是否把多个独立故事强行放入一张 Card，以及是否存在明显证据缺口。此阶段不得修改项目文件或运行时数据。

若选题以“文明中的第一次”为入口，必须在内部将“第一次”归入以下一种，并按该强度写标题与正文：

- 目前已知最早；
- 现存材料中最早的一批或之一；
- 早期关键转折点。

标题不得提出一个确定的“第一”，再在正文中暗中撤回。证据只支持“之一”或“关键转折”时，标题也必须相应收窄。

## 4. 第二阶段：来源、Claim ledger 与完整待审正文

本阶段把来源审查与完整正文合并为一次审稿，但不得把研究和写作混成一遍完成。一个阶段、一次提交，不等于一次同时写完。Agent 必须在内部依次完成：

1. **证据整理遍**：核对来源，建立 Claim ledger，确定证据强度与去向，记录 EditorialReview、Event、Entity 和关系；
2. **故事写作遍**：先形成 Scene 故事骨架，只使用标记为 `public` 的 Claim 写 Card 和完整 Scene 的标题、顺序与正文；Scene 通常为 `3–11` 个，但以叙事完整性为准，不得逐条翻译 ledger；
3. **公共文字删减遍**：删除不推动故事的专名，把可替代的名称改成日常指称，移出学者姓名、学派、争论目录和非必要限定，并核对每个 Scene 是否由具体行动、处境或变化推进。

三遍完成后，在同一轮先提交公共故事骨架与完整正文，再提交来源、Claim ledger 和其他内部审稿材料，等待一次批准。来源、Claim 与正文不拆成两次用户审批。

每条 Claim 至少记录：

- 稳定 ID 或临时编号；
- 证据允许采用的最窄正面表述；
- 类型：事实、学术解释、编辑综合、不确定性或叙事过渡；
- 支持它的来源；
- 证据强度与适用范围；
- 去向：`public`、`editorialReview`、`dataOnly` 或 `delete`；
- 关联的 Card 或 Scene。

来源应尽量靠近具体 Claim。Card 或 Scene 的来源列表可以汇总 provenance，但不能替代 Claim 级来源。

Claim ledger 同时是写作边界：公共正文只能使用去向为 `public` 的 Claim，且不得比其中的正面表述更确定、更广泛或更具因果性。不确定性、争议、反例和替代解释默认进入 `editorialReview`；数据关系默认进入 `dataOnly`。来源不足的内容不得以公共不确定性的形式留在正文；若有内部审稿价值则进入 `editorialReview`，否则标记为 `delete`。不得用流畅叙事掩盖证据缺口。

来源清单中的材料限制应标为“内部使用边界”。这一栏用于来源审查和证据控制，不得直接改写为公共正文中的防御性段落。现代学者姓名可以正常保留在来源清单中，但不能因此自动进入故事正文。

每个拟定 Scene 必须至少有一项来源。来源数据可以暂时不向读者呈现，但必须进入数据和验证层。

本阶段仍只输出人类可读的来源、ledger 与待审文字；不得选择、展示或审核图片、地图及其他媒体素材。Scene 数量由该 Card 的重要性与完整叙事需要决定，不得为了凑数量机械拆分，也不得为了压缩数量遗漏故事成立所必需的情节或解释步骤。

### Card

- 形成一个完整、聚焦且可独立阅读的故事；
- 公共标题简洁、陈述性，不使用冗长问题；
- 引言通常为一至两句话，只负责打开故事入口；必要背景放入第一个 Scene；
- 有明确的内部编辑目的，但不必向用户显示 guiding question；
- 引言和核心叙事不超过来源与 Claim ledger 的支持范围；
- 至少包含两组有来源支持的历史案例或证据；
- 至少有两项可信来源；
- 必须包含内部 EditorialReview；
- 导航只保留有明确叙事价值的下一步。

Card 关联的 Event、Entity 和 StructuralEdge 是内部数据映射，不是公共正文点名清单。相关对象尚未拥有独立 Card，不妨碍它在当前故事中出现；当前 Card 只需解释它与眼前故事的关系。若当前只需提及，可以不建立导航；若关系或未来导航需要稳定身份，可以先建立最小但准确的 Entity 或 Event，并由后续内容复用同一 ID。

Card 可以暂时没有出站导航，但不能没有 Event。V5 不在 Card 上手写 `eventIds`：每个 Scene 必须有非空 `eventIds`，且至少一个所引 Event 的规范化时间与该 Scene 相交；Card 的 Event 集合按 Scene 顺序去重推导。同一个 Event 可以服务多个 Scene，不得为了满足形式要求虚构一次性 Event。文本形成与流传使用 `textualTradition`，传统叙事情节使用 `traditionalNarrative`，不得伪装成有同时代证据的历史事件。

### Scene

每个 Scene 的待审材料必须写明：

- 标题；
- 时间范围、纯年份 `timeSpan.label` 与 `timeDisplay`。`timeDisplay` 默认为 `year`，界面显示该 label；只有史诗或神话内部情节没有可考历史发生年份时，才使用 `undatedNarrative`，界面固定显示“叙事时间 · 无可考年份”。不得自定义这行文案；
- 当前读者问题；
- 叙事任务；
- 具体行动、处境或变化；
- 允许进入公共正文的 Claim ID；
- 完整正文；
- 来源。
- 一个或多个 Event ID，以及其中至少一个 Event 与本 Scene 的时间相交的核对结果。

完整正文应直接接受审稿，并核对没有越过 ledger 的证据边界。不为每个 Scene 设置负面结论上限或逐段防御性审校栏，以免审稿结构把公共文字推向学术答辩。

Scene 还必须满足：

- 每个 Scene 只承担一个有限的历史情境或解释步骤；
- 每个 Scene 的 `timeSpan.label` 必须与数值 `start`／`end` 一致并统一写成纯年份；`approximate: true` 时以“约”开头。默认由它提供标题上方的小字；`undatedNarrative` 只改变公共显示，不删除内部年代；
- 正文建议为 `50–150` 字，不含标题、图片说明和界面文案；
- 正文优先以具体的人、物件、行动、处境和变化推进；每个保留的专有名字必须承担人物关系、事件推进、历史判断或跨故事连接中的明确作用，不用名词堆叠代替叙事；
- 专名审查不设置跨 Card、跨内容包或整张 Card 的数量上限。相关扩展包是否已经制作，不影响当前故事使用必要名称；真正需要控制的是没有叙事作用的名称和同一句中的连续堆叠；
- 默认读者不熟悉历史，但对历史感兴趣，并可能从当前 Card 直接进入。首次出现且无法省略的名称，必须用日常语言交代它是谁或是什么、正在做什么，以及为何在当前故事中出现；如果多个名称都不可删除，应调整顺序逐个引入；
- Scene 顺序共同形成 Card 的完整叙事；
- 正文避免重复结论和“takeaway”式复述；
- 除非当前故事本身讲述史学史、思想史、考古研究史或某位学者，现代学者姓名、学派、观点阵营和争论过程不得进入公共 Scene；
- 面向读者的正文使用证据支持的最窄正面表述。只有不作限定就会把推测写成事实、扩大时间空间或因果范围，或强化会误导主线的流行说法时，才保留一句紧贴事实的最短澄清；其余限制、反例、不确定性与其他解释全部写入内部 EditorialReview；
- Scene 通常以行动、处境变化或新的历史问题结束，不以研究警告代替叙事收束；
- Scene 不是独立于 Card 的公共故事；
- 每个 Scene 至少有一项来源，即使暂时不向读者显示。

### Event、Entity、关系与导航

- Event 应具有稳定、简洁的事件身份，明确时间、参与者、证据、关系和来源；
- Event 必须在 `historicalEvent`、`historicalProcess`、`textualTradition`、`traditionalNarrative` 中选择准确的 `kind`；
- 区分同时代证据、后世传统和现代学术解释；这一内部区分不要求公共正文点名现代学者；
- 不把多个解释压缩成唯一因果链，也不因此在公共正文罗列所有学术路线；正文采用不超过证据范围的综合表述，完整替代解释进入 EditorialReview；
- 不为相同事件重复创建仅 ID 不同的副本；
- 只列出叙事真正需要的 Entity 和 StructuralEdge；
- `政治实体`（`polity`）与 `文化传统`（`culturalTradition`）的 `canonicalSummary` 必须以规范化年代开头，并与该 Entity 的 `timeSpan.label` 完全一致，格式为“（约）公元前……—前……年，……”；若实际时段跨越公元前后或不适用该格式，则仍须先写与 `timeSpan.label` 一致的年代，再接中文逗号和简介；
- NavigationOption 必须说明下一个视角的价值，并标明建议出现位置。
- 面向读者的导航使用“进入”而不是“返回”或“回到”，因为读者可能从任意 Card 开始漫游；
- 公共导航默认从目标 Card 的第一个 Scene 开始；`target.sceneId` 本身只标明最相关的段落。只有经过明确批准的特例才可增加 `entry: { kind: 'targetScene' }`，直接进入该段落；
- 同一张 Card 内不得出现两个指向同一目标 Card 的可见链接；
- 两张 Card 之间只要一方提供进入另一方的可见链接，另一方也必须提供语义明确的反向链接。反向链接不必出现在对应 Scene，也不必使用对称文案，但必须具有独立的叙事价值。

### EditorialReview

完整故事必须在内部记录至少一项 limitation、counterexample、uncertainty、dispute 或 alternative explanation。这些内容进入数据与验证层，但当前版本默认不向用户显示。

不得通过把上述内容写入公共正文来满足内部 EditorialReview 要求。公共正文若确需保留限定，仍须同时在内部记录其完整依据、适用范围和替代解释。

本阶段不得分配最终 ID，不得机械转换为完整 JavaScript 数据，也不得修改项目文件或运行时数据。完成后停止并等待用户批准。

## 5. 第三阶段：媒体、置入、验证与复盘

第二阶段正文获批且用户明确要求进入第三阶段后，根据已批准的 Scene 叙事任务选择媒体，随后直接置入 V5、完成验证和流程复盘。本阶段不得擅自改写已批准正文。第三阶段默认连续执行；只有媒体缺口、AI／自制示意图需要明确批准，或 schema、validator、renderer 无法忠实表达方案时，才暂停相关部分并请求用户决定。

每个 Scene 的媒体待审材料必须写明：

- 媒体类型：图片、地图、其他媒体，或请求用户明确批准纯文字；
- 媒体的理解目的：它具体帮助读者看懂正文中的什么；
- 素材方式：复用现有本地素材、寻找现成历史素材，或用户明确批准的示意图；
- 候选检索记录：对新历史素材和既有素材复用，至少记录两个实际查看过的博物馆、大学、档案馆或许可清楚的候选，以及选择／不选择理由；
- 来源、许可、创作者、年代、历史对象对应关系与可下载性；
- 拟用的 title、alt 和必要 caption；
- 图片的原始宽高与展示方式；
- 地图所需的图形编码、文字标注、近似性说明和证据来源；
- 现有 schema、validator 与 renderer 能否忠实表达该方案。

媒体还必须满足：

- 媒体必须绑定到具体 Scene，并说明它帮助读者理解什么；
- 不因为现有界面支持地图就强行加入地图；
- 图片、地图或文字之间的切换必须对应当前 Scene；
- 除非用户明确批准，Scene 的媒体类型不得为纯文字；媒体应优先选择能够直接帮助理解当前 Scene 的图片或地图；
- 选定图片素材时，必须在第三阶段最终验收中列明实际图片、来源与许可；方案必须按图片原始比例完整展示，不得用裁切、放大填充或局部截取代替完整画面；
- 不得把“优先复用”理解成跳过检索。复用现有本地素材前仍须与至少两个合适候选比较，并在交接记录中说明复用为何比新素材更适合当前 Scene；没有检索记录的复用不通过模块门禁；
- 同一张物理图片在整个当前 V5 中最多用于两个 Scene。重复次数按原始图像和本地 `src` 判断；为同一文件新建不同 Asset ID、改写 title 或 alt、裁切、转码，都不视为新素材。选图时应优先为承担不同叙事任务的 Scene 补充真正对应的新画面；
- 地图暂时不要求逐张渲染后展示，但必须提交完整的地点、点线面编码、文字标签、图例、近似性说明和来源；
- 除非用户特别说明，否则不制作示意图；优先寻找来源、许可和历史对应关系清楚的现成素材。找不到合适素材时，不得自行改用纯文字，也不得用自制示意图占位，应把媒体缺口提交用户决定；
- 若使用 AI 生成图片，必须在本阶段明确标注并提交实际画面审核；不得把生成图暗示为历史实物、同时代肖像或考古复原定论。

若当前模型、validator 或 renderer 不能忠实表达方案，应标记为“实现问题”并暂停相关部分，不得以无效数据绕过冲突。除这些明确例外外，不得用“等待媒体确认”把第三阶段拆成额外审批轮次。

媒体方案确定后，在同一阶段继续置入，不另设审批点。

### 并行任务的集成所有权

多 Agent 并行生产时，必须遵循 `AGENTS.md` 的 Multi-agent content integration ownership。主运行时在每一个完成的集成边界都必须有效；尚未完成的模块留在主聚合路径之外。

- Content Agent 只编辑获分配的 `data/<内容模块>.ts`、对应的 `assets/images/<内容模块>/`、模块专属测试和本 ContentPack 记录；不得修改 `index.html`、`src/main.ts`、`src/data/atlas-data.ts`、其他内容模块、既有模块中的共享或反向导航，以及固定集成测试；正式内容模块统一使用 TypeScript；
- UI Agent 的常规测试应使用小型、稳定且有效的 fixture，不依赖正在被 Content Agent 修改或暂时无效的全集数据；接入完成后才用实时聚合 atlas 做集成级 smoke test；
- 同一时间只能有一个 Integration Agent 拥有 `index.html`、`src/main.ts`、`src/data/atlas-data.ts`、固定加载顺序测试、跨模块与反向导航、全局 ID／引用消歧，以及受加载顺序影响的共享验证清单；
- Content Agent 若需要跨模块连接，应在交接记录中提出出站入口、目标 ID、所需反向入口和建议位置，不得直接修改既有模块；
- Content Agent 可以在交接记录中提出“首页候选”及其叙事理由，但不得直接修改首页策展配置。首页入口不会因新增 Card 自动增加；只有当前 UI／Integration 所有者可以调整入口，而且配置只保存稳定 Card ID，公共标题与摘要始终从聚合数据读取；
- 模块交给 Integration Agent 前必须冻结编辑所有权。Integration Agent 仅可为引用接线、稳定 ID 复用和跨模块导航调整临时编辑已提交模块，不得改写已批准公共正文和媒体选择；若需要编辑性改写，必须先把所有权退回 Content Agent。

新建、staging 或多 Agent 并行模块进入主聚合器前必须独立通过模块级门禁。单 Agent 连续修改已经接入的活动模块时不追溯要求隔离门禁，但仍须通过主运行时全量门禁：

1. JavaScript 语法；
2. 模块导出或浏览器全局初始化；
3. 模块内部重复 ID；
4. Source、Asset provenance、本地路径与文件存在性；
5. 模块内部引用；
6. 把全部顶层引用分类为模块内部、当前活动 atlas 已有、或尚未接入的并行 sibling；当前 atlas 引用由脚本自动发现，只有 pending sibling 引用需要在全部十四个可引用集合下显式声明；声明未使用和使用未声明都必须失败；
7. 适用的模块专属负向测试。

模块级通过只表示“可交给集成”，不表示已经进入主运行时。交接记录必须包含模块文件、预期加载位置、导出全局名、新增顶层 ID、复用外部 ID、拟议出站导航、既有模块所需反向导航、本地 Asset 目录、模块级测试结果和未解决问题。机器可读交接文件使用 `handoffVersion: 2` 的 `docs/content-packs/<module>.handoff.json`，结构参考 `docs/content-packs/module-handoff.example.json`。门禁会把这些声明与模块实际导出、活动 atlas 引用和浏览器全局初始化逐项核对；执行：

```text
node scripts/validate-content-module.js data/<module>.ts docs/content-packs/<module>.handoff.json
```

每个 `assets/images/<module>/` 还必须包含非运行时、`manifestVersion: 2` 的 `manifest.json`，为 Asset 保存 creator、license、sourceUrl、origin、原始宽高、编码后宽高、编码后字节数、`webp` 格式、SHA-256、来源 ID 和审核状态。现存 V4 迁移到 V5 的素材可以诚实标为 `needsMetadataAudit`，但新模块必须在门禁前完成审核，不得猜测许可或创作者。

Integration Agent 接手后必须先确认当前主运行时有效，再接入 `src/main.ts` 和聚合器、解决全局重复 ID 与外部引用、置入反向导航、更新加载顺序测试，随后运行完整 validator、类型与语法检查、全量测试、正式构建和 `pnpm test:browser` 生产浏览器门禁；自动冒烟未覆盖的桌面、移动、历史导航、键盘与 reduced-motion 行为仍须人工验收。最后同步 README、架构文档和受影响工作规范。

已经通过模块级门禁但尚未完成主运行时门禁的模块，必须在任务或 ContentPack 交接记录中标记为“集成中”。这不是 runtime schema 字段；除非 schema 正式采纳并校验，不得添加 `integrationStatus`。集成中的模块不得部分加载到 `src/main.ts` 或 `src/data/atlas-data.ts`，不得通过 renderer 过滤、查询静默跳过、try/catch 压制或删除无效对象来掩盖未完成接入。

### 置入 V5

用户已在第二阶段审核来源、Claim ledger、标题、事实与解释的区分、Scene 分工、完整文字、Event 稳定性、导航价值和内部限制。进入第三阶段的授权同时允许 Agent 为已批准正文选择合规媒体并置入；若第二阶段只批准部分内容，只能置入已批准部分。

置入时应：

- 忠实转换已批准文字，不擅自改写核心观点；
- 按当前 V5 数据模型分配稳定且可读的 ID；
- 严格遵循第一阶段批准的数据文件决策；
- 若新建内容文件，明确其聚合方式和脚本加载顺序；
- 复用已经存在且语义相同的 Entity、Event、Source 和 Asset；
- 补齐 Scene—Event、Card—Scene、Source、Navigation 和媒体之间的引用；Card Event 必须由 Scene 推导，不得在 Card 重复维护；
- 保持 Card 对 Scene 所有权和顺序的唯一权威来源；
- 不因布局方便增加地图或虚构地理锚点；
- 不把内部 EditorialReview 默认渲染给用户；
- 不做未获批准的数据结构重构或文件拆分。

若现有结构无法忠实表达已批准内容，应暂停并报告冲突，由用户决定是否调整内容或另开结构改造任务。

### 图片规则

图片正式置入前必须确认来源、许可、真实宽高、alt、title 和必要 caption，并下载为项目内本地文件，运行时不得请求远程 URL。后世艺术形象不得暗示为历史人物的同时代肖像。

运行时 Scene 图片统一使用本地 `.webp`。每张编码后文件必须严格小于 `500,000 bytes`，编码后的任一边不得超过 `2560` 像素；转换不得改变已经批准的裁切范围、宽高比、构图或叙事内容。照片、线稿、地图和带透明区域的插画不得机械使用同一个质量参数，必须检查实际 WebP 在 desktop 与 mobile 媒体栏中的细节、文字、细线、透明背景和色彩。引用、manifest 与测试全部通过后，应删除同目录中不再使用的 JPEG／PNG 运行时副本，避免仓库和部署产物同时保存两份。

同一张物理图片在整个当前 V5 中最多用于两个 Scene。重复次数按原始图像和本地 `src` 判断；不同 Asset ID、title、alt、裁切或转码不能绕过上限。置入与验证阶段必须用自动化检查拒绝超出上限的内容。

AI 生成图片同样遵守上述 WebP、尺寸和体积规则。生成原图超出上限时，必须先压缩或转换格式，再写入 Asset；压缩不得擅自改变已批准的构图、宽高比或叙事内容，并须检查实际界面显示质量。

所有 Scene 图片都按原始比例完整显示并在媒体栏居中，不得为填满容器而裁切；图片之外的余白统一使用地图大陆色 `#c8cbbb`。这一规则须同时验证 desktop 和 mobile。

每个拥有 `assets` 集合的内容数据文件必须拥有自己的图片目录，统一使用 `assets/images/<数据文件名>/`。该文件声明的图片 Asset 只能引用自己的目录；新增或迁移内容模块时必须同步更新路径、入口脚本与自动化校验。

### 地图规则

- 只有空间信息确实改善当前 Scene 时才使用地图；
- 地图不是内容包或 Card 的完成条件；
- **所有地图标注必须同时包含图形与文字两部分。** 点、线、箭头、色块、纹理等图形负责显示位置、方向、范围或关系；就地标签或紧邻地图的简短图例必须直接说明每一种图形代表什么。不得只画图形让读者猜测，也不得只用一段文字代替图上的视觉区分；
- 当一张地图同时使用点、线或色块中的两种以上时，必须逐项写明“图形样式＝含义”。重要地点优先在图上直接标名；近似路线、教学范围与非边界性色块还须用一句最短说明交代表达边界；
- `locatedAt`、`associatedWith`、`screenCallout` 必须保持区分；
- 推测边界、路线、锚点和教学覆盖必须明确标记为 approximate；
- 地图数据不能代替文字证据。

### 验证、流程复盘与新增 content 方向

每次置入至少执行：

- V5 完整 validator；
- 重复 ID 与悬空引用检查；
- Scene—Event 时间相交、Card—Scene 所有权与 Card Event 推导检查；
- Source 和 ClaimBlock provenance 检查；
- Asset 本地路径、文件存在性和许可检查；
- 全量 Node 测试与 JavaScript 语法检查；
- direct Card/Scene hash 检查；
- back/forward 与滚动恢复检查；
- desktop、mobile 与 reduced-motion 视觉检查；
- 浏览器控制台错误检查。

阶段结果应分为三部分：

### 内容与实现验收

- 新增 Card 的直接地址；
- 新增或复用的 Event 和 Entity；
- 媒体与来源清单；
- 测试结果；
- 未完成或无法实机验证的事项。

### 流程复盘

把建议严格分为“通用规则”“当前选题特例”“实现问题”“尚待验证”。未经用户批准的通用规则不得写入本指南。

### 新增 content 方向

基于本次内容包实际出现的人物、事件、制度、地点、思想或关系，提出若干可以继续漫游的新 Card 方向。每项应说明：

- 推荐的主题或暂定标题；
- 它从当前故事的哪个具体线索出发；
- 为什么值得读者继续点开；
- 可能的主 Entity、Event 或连接目标；
- 当前已有的来源基础与仍需研究的问题。

这些方向只是下一轮选题候选，不得在第三阶段未经批准直接置入。用户完成最终阅读验收后，本次内容包才视为完成。

## 6. 可直接复制给 Agent 的提示词

### 开始一个三阶段内容任务

```text
请按照 docs/CONTENT_PACK_AND_AUTHORING_WORKFLOW.md，
为【主题】启动 Civilization Wander V5 正式内容任务。
内容包规划入口 Entity 暂定为【entity】；每张 Card 的主 Entity 将在选题简报中分别确认。时间范围是【范围】。
先检查实际运行时，并让我确认数据写入哪个文件、是新建还是复用。
严格按三阶段推进，每阶段完成后停止并等待批准。第二阶段把来源、Claim ledger 与完整正文合并提交；第二阶段获批并进入第三阶段后，连续完成媒体、置入、验证、复盘与新方向建议。
第二阶段内部依次完成证据整理、故事写作和公共文字删减，但仍在同一轮提交并等待一次批准。Claim 必须标记为 `public`、`editorialReview`、`dataOnly` 或 `delete`；公共正文只能使用 `public` Claim。
专名是否可以出现，只看它是否推动当前故事，不看相关 Card 或扩展包是否已经制作。删除不影响人物关系、事件推进、历史判断或跨故事连接的名称；不要设置跨 Card 或整包的专名数量上限。
现代学者姓名、学派和学术争论默认只进入来源或 EditorialReview。公共正文只写证据支持的最窄正面叙事，不逐条翻译证据边界和来源限制。
若启用多 Agent 并行，每个 Content Agent 只编辑自己的内容模块、对应 Asset 目录和模块专属测试；同一时间只指定一个 Integration Agent 修改 `index.html`、`src/main.ts`、聚合器、固定加载顺序测试和共享导航。未完成模块保持在主聚合路径之外，并在非运行时交接记录中标记为“集成中”。
在第二阶段正文获批准且我明确要求进入第三阶段前，不要修改项目文件或运行时数据。
每轮将内容产物和流程改进建议分开。
```

### 置入已批准内容

```text
请按照 docs/CONTENT_PACK_AND_AUTHORING_WORKFLOW.md，
将本任务中已经明确批准的正文与媒体方案置入当前 V5 数据。
不要改写已批准文字；严格遵循第一阶段批准的数据文件决策。
如有结构冲突，先报告，不要自行重构数据结构。
补齐稳定 ID、来源、Scene—Event 引用、Card—Scene 所有权、导航和本地 Asset；不要在 Card 上手写 Event 列表。
若内容由其他 Agent 并行生产，先核对模块级门禁、交接记录和所有权冻结；只有当前唯一 Integration Agent 可以修改 `index.html`、`src/main.ts`、`src/data/atlas-data.ts`、共享导航及固定集成清单。不要把“集成中”写入 runtime schema，也不要用 renderer 过滤未完成模块。
随后在同一第三阶段完成验证、流程复盘并提议新增 content 方向。
```
